Why does this exist

Because "it works on my machine" has a stupider cousin: it worked before I pasted it. A command with a --flag goes into a Word doc, autocorrect turns the two hyphens into an em dash, someone copies it into a terminal, and it fails with an error that mentions nothing about dashes. The text looks correct in every window it passes through. That is the whole problem — the damage is invisible at every step except the last one, where it is someone else's problem.

The four things that actually get you

  • Smart quotes. ' becomes ’. A shell sees a literal character, not a quote, so the argument never terminates.
  • Dashes. --verbose becomes –verbose. Every flag parser rejects it, and no error message will say why.
  • Markdown. Slack and Jira read _ and * as formatting, so my_var_name arrives as myvarname with the underscores deleted. The text is not mangled, it is missing.
  • PDF ligatures. Copying define out of a PDF can give you a single ﬁ glyph where fi should be. It looks perfect and matches nothing.

When does this actually happen?

Mostly when text is authored or retyped somewhere, not when it passes through untouched. Word and Google Docs autocorrect as you type, so a command someone typed into a runbook is already broken before you copy it out. Slack and Jira apply their formatting when the message is sent or rendered. PDFs do their damage at extraction time. The everyday version of this is copying a command out of a wiki page a colleague wrote by hand.

Is this accurate?

These are the standard, default-on behaviours of each destination, and every rule is labelled with what it did and why. They are not exhaustive — autocorrect is configurable, Slack's formatting can be disabled, and PDF extraction varies wildly by producer. Treat a clean result as "nothing obvious will break", not a guarantee. Where a destination's behaviour depends on a setting, the note says so.
