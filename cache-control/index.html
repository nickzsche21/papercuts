The misunderstandings that cause most caching bugs

no-cache does not mean "do not cache"

It means "you may store this, but you must revalidate with the server before every reuse." The response is written to disk. The directive that actually prevents storage is no-store. Confusing these two is the single most common caching mistake — the Stack Overflow questions comparing max-age=0 with no-cache, and no-cache with must-revalidate, have over 770,000 views between them.

Sending no headers at all does not mean no caching

If a response has no Cache-Control and no Expires but does have a Last-Modified, browsers apply heuristic freshness — typically a tenth of the time since the file was last modified. A file edited a year ago becomes cacheable for over a month, without anybody choosing that. This is why "I didn't set any caching" and "my users are seeing an old version" are the same bug.

A normal reload is not the same as a revisit

Pressing reload makes the browser revalidate even when the response is still fresh, so testing your caching by hitting reload tells you almost nothing about what a real returning visitor experiences. A hard reload goes further and ignores the cache entirely. Navigating to the page from a link is the only path that shows real cache behaviour.

must-revalidate on its own does nothing

It governs what happens after a response goes stale. With no max-age and no Expires there is nothing to define staleness, so the directive never takes effect. It is not a way to force revalidation — that is no-cache.
