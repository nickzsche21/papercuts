Why a normal diff is useless on a CSV

Text diffs compare line by line and in order. A database export has no guaranteed order, so re-running it can move every row and produce a diff where everything is red and green and nothing is informative. Insert one row at the top and every subsequent line is reported as changed.

The operation you actually want is a join. Match rows by a stable identifier, then compare the matched pairs field by field. That is what this does — and it is why row order is ignored completely here.

What is a good key?

Any column whose values are unique and stable: an id, a SKU, an email address, an order number. The tool guesses by looking for a column whose values are unique and complete in both files, and you can override it. Composite keys work too — pick more than one column when no single column is unique on its own.

What if the key is not unique?

You are told rather than given a wrong answer. Duplicate keys make the pairing ambiguous, so the affected rows are reported instead of being silently matched to whichever row came first.

What about columns that were added or removed?

Reported separately. Only columns present in both files are compared for changes, so adding a column does not make every row look modified.

Does my data get uploaded?

No. Both files are parsed and compared in this tab, with no server and no network request.
