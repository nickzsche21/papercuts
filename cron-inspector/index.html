Your whole crontab, at once

Every cron tool explains one expression. This one takes the whole file and tells you what actually matters: which jobs land on the same minute, which get skipped or run twice by daylight saving, and which never run at all.

The three cron bugs nobody catches by reading

1. Everything fires at 3am

Crontabs grow one line at a time, and every line picks a quiet hour. A year later, eleven jobs start simultaneously at 0 3 * * *, saturate the disk, and the one that matters times out. Nothing in the file looks wrong; you have to line the schedules up to see it.

2. Daylight saving eats the job

Cron runs on wall-clock time. When the clocks go forward, the 2am–3am hour does not exist, and a job scheduled inside it is silently skipped for the year. When the clocks go back, that hour happens twice and the job can run twice. If it is a billing run or a report, both outcomes are bad. This tool finds the actual transition dates for your timezone and tells you which lines land in the gap.

3. The day-of-month / day-of-week OR trap

If both the day-of-month and day-of-week fields are restricted, cron runs the job when either matches, not both. So 0 0 1 * MON is not "the 1st, if it is a Monday" — it is "the 1st, and every Monday". This surprises almost everyone, and it is flagged wherever it appears.

The tool also catches expressions that can never fire at all — 0 0 30 2 * waits for the 30th of February forever.

Which cron dialect is this?

Standard five-field Vixie/POSIX cron, the flavour used by Linux, macOS, most Docker images and most CI schedulers. Six-field expressions (Spring and Quartz, where the first field is seconds) are detected and read as such. Names like MON and JAN, step values, ranges, lists and the @daily-style macros all work.

Does anything leave my browser?

No. Parsing and every fire-time calculation happen in this tab, using the browser's own timezone database.
