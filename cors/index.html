The four things nobody tells you about CORS

1. It works in Postman because CORS does not exist outside a browser

CORS is enforced by the browser, not by the server. curl, Postman, your backend tests and your mobile app will all succeed against an endpoint that a browser refuses to read. That is not evidence the server is configured correctly — it is evidence you are not in a browser. The request usually reached the server and the server usually answered; the browser simply refused to hand the response to your JavaScript.

2. The fix is always on the server being called

You cannot fix CORS from the calling page. Not with a fetch option, not with a meta tag, not with a header on your own site. The server at the other end has to opt in. If you do not control it, your only real options are a proxy on your own origin or the API vendor's dashboard — everything else is superstition. This is the single most common wasted afternoon in web development.

3. There are often two requests, and the first one is invisible

Anything beyond a "simple" request makes the browser send an OPTIONS preflight first. Sending Content-Type: application/json is enough to trigger it, which is why almost every JSON API needs preflight handling. The preflight carries no cookies and no Authorization header — so if your auth middleware runs before your CORS middleware, it returns 401 to the preflight and the real request is never sent. The browser reports this as a CORS error, which sends people looking in entirely the wrong place.

4. * and credentials are mutually exclusive

The moment you set credentials: 'include' or withCredentials = true, the wildcard becomes illegal. You must echo the caller's exact origin back, add Access-Control-Allow-Credentials: true, and — critically — send Vary: Origin, or the first origin to hit your CDN gets its Access-Control-Allow-Origin cached and served to everybody else.
