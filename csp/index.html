Why CSP is so hard to fix correctly

The fast fix deletes the entire point of CSP

Almost every CSP problem can be silenced by adding 'unsafe-inline' to script-src. It works instantly, and it turns off the protection that CSP exists to provide — inline script injection is precisely the attack the policy was blocking. This tool always offers a nonce or a hash first, and marks 'unsafe-inline' as the last resort it is.

A nonce silently disables 'unsafe-inline'

If a source list contains both a nonce or hash and 'unsafe-inline', browsers ignore 'unsafe-inline' entirely. This is deliberate — it lets you serve a strict policy to modern browsers and a permissive one to old ones — but it catches people constantly: you add a nonce, your other inline scripts break, and the policy looks like it should have allowed them.

The fallback chain is not obvious

script-src-elem falls back to script-src, which falls back to default-src. But several directives — notably frame-ancestors, form-action and base-uri — do not fall back to default-src at all. If you never set them, they are unrestricted no matter how strict the rest of your policy is. That is why base-uri 'none' matters: without it, an injected <base> tag can redirect every relative script URL on the page.

Test in report-only mode first

Ship Content-Security-Policy-Report-Only before Content-Security-Policy. The browser reports what it would have blocked without breaking anything, so you can collect real violations from real users instead of guessing. Every generated policy here comes with the report-only version too.
