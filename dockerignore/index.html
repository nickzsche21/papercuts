Docker · Build context

COPY failed: file not found in build context

The file is right there. Paste your .dockerignore and your paths, and find out which line excluded it — and whether you have hit the trap where node_modules means something different here than it does in .gitignore.

The trap almost everyone hits

.dockerignore and .gitignore look like the same file. They are not, and the difference is the single most common cause of a build that copies gigabytes it should not, or fails to copy a file that is plainly on disk.

Patterns are anchored to the context root

In .gitignore, a bare node_modules matches a directory of that name at any depth. In .dockerignore it matches only ./node_modules, at the top of the build context. A nested app/node_modules or packages/ui/node_modules is copied in full, which is how a monorepo image quietly gains a gigabyte. To get the git behaviour you have to write **/node_modules.

There is exactly one of them

.gitignore works per-directory — you can drop one in any subfolder and it applies from there down. .dockerignore does not. There is one file, it lives at the root of the build context, and a .dockerignore in a subdirectory does nothing at all. If yours is next to the Dockerfile but the build context is the repository root, it is being ignored entirely.

The last matching line wins

Order decides everything, exactly as in git. A broad * placed after !keep.txt silently re-excludes the file you were trying to keep, and the result below names the exact line that made the final call.

Other reasons COPY cannot find a file

  • The path is outside the build context. COPY ../shared/x.json can never work — the daemon only receives what is inside the context directory, and there is no way to reach above it.
  • The context is not what you think. In docker build -f docker/Dockerfile . the context is ., so every COPY source is relative to the repository root, not to the Dockerfile.
  • Case. The daemon matches case-sensitively even when your filesystem does not, so a build that works on a Mac fails in CI.
  • It is untracked but present. Docker copies from the filesystem, not from git — being in .gitignore does not exclude a file from the context, only .dockerignore does.

How exact is this?

The matcher here implements Docker's documented rules: patterns relative to the context root, Go-style *, ? and character classes that do not cross a separator, ** spanning directories, ! exceptions, and last-match-wins. It is a reimplementation, not the daemon — Docker was not available on the machine this was built on, so unlike the sibling tools it could not be differentially tested against the real thing. Treat the line attributions as reliable and the exotic edge cases as advisory.
